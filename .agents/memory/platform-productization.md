---
name: Smith platform productization
description: Owner's new multi-server product scope and rollout boundaries.
---

The Owner wants the existing Smith application productized into a commercial
multi-server platform with Discord OAuth, a web dashboard, configurable modules,
analytics and premium-entitlement/billing readiness.

**Why:** The uploaded platform upgrade requirements explicitly expand the former
single-server scope while requiring Hallowed Core to remain stable.

**How to apply:** Preserve Hallowed Core's three frameworks, single self-selected
primary and human-approved extras as a policy adapter. Do not weaken existing
protected-account/hierarchy rules or discard native onboarding/history. Use the
same Discord application and one Gateway client per bot process. No active
charging, aggressive public installation or sharding in this phase. Multi-server
support cannot be declared complete until Hallowed Core and a separate test guild
have both been verified. Web configuration must never bypass existing guarded
Discord mutation services.

The former controlled LMOC acceptance authorization was revoked on 2026-10-15.
Hallowed Core is now Smith's sole active production guild. LMOC configuration
is historical/reference-only; preserve the six-step handoff and all historical
records, without heartbeats, activation, command registration, analytics
collection or Discord writes. Any later test guild requires explicit Owner
authorization.

**Why:** The Owner explicitly retired LMOC and required safe archival without
deleting evidence or LMOC TEST records.

**How to apply:** Do not use prior installation, reviewed release bundles,
environment allowlists or historical acceptance instructions as new activation
approval. Preserve Hallowed Core's native runtime and the single-Gateway rule.
Distinguish prepared source/settings from the still-running published version;
publishing remains Owner-controlled.

Configuration promotion must be limited to LMOC TEST's reviewed configuration,
never a copy/reset of the development database or member/consent/activity history.
Previously imported configuration must not be reset over later production Owner
edits when the bot restarts.

**Why:** The Owner explicitly authorized copying only the test guild's setup and
15 configurations while requiring Hallowed Core, real records and production
behavior to remain intact.

**How to apply:** Separate the supported publish-time schema review from
configuration data transfer. Refuse conflicting production configuration rather
than silently replacing it; require real post-release per-guild acknowledgment
and live human actions before declaring acceptance.

Private previews must distinguish stored configuration from active runtime
behavior and credential availability from successful Discord authentication.

**Why:** Discord may have valid credentials but no registered OAuth callback.
The Owner's acceptance condition is working behavior in two guilds, not screens
or successful simulated tests.

**How to apply:** Mark unconnected module adapters as inactive/draft, describe
browser-intercepted checks as synthetic, and obtain an authorized second guild
before claiming commercial multi-server readiness.

SDK permission objects may be hydrated by a REST-only dashboard client, but that
client must have no Gateway session and must reject all Discord REST writes.

**Why:** A development dashboard runs while the published bot remains online.
Logging in another client would violate the single-Gateway rollout boundary;
giving the preview client write access would create a second mutation authority.

**How to apply:** Keep permission hydration separate from privileged execution.
Production web actions reuse the already-connected, guarded bot and its actual
guild services; do not make the read-only preview client privileged just to enable
an unsupported dashboard control.

The Owner formerly authorized LMOC TEST for separate-guild verification; that
authorization is revoked. Hallowed Core must not be used as its own second-guild
proof.

**Why:** The Owner explicitly changed the production scope to Hallowed Core only.

**How to apply:** Seek explicit authorization for a future test guild before
controlled multi-server verification. Historical LMOC evidence is for review,
not permission to resume tests.

Preserve all current production access while implementing the entitlement
architecture. Do not infer or enforce final FREE/PRO/ULTIMATE restrictions from
the proposed marketing page yet. Use isolated fixtures to test tier gating until
the Owner explicitly approves the production feature matrix.

**Why:** The Owner explicitly selected this production-access boundary.

**How to apply:** Separate configurable entitlement mechanics from an approved
production policy. Do not assign live plans, enable restrictive production rules,
activate modules or publish merely to demonstrate fixture gating.
