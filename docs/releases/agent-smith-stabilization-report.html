1. Setup 500 root cause and request trace

The old wizard sent PUT /api/platform/guilds/{guildId}/setup, with modules and log/welcome channel selections. The server resolves the OAuth session, checks CSRF and guild authority, validates input, then calls the setup service.

Production SELECTs confirmed that Hallowed Core has zero platform guild rows, zero platform module rows and zero setup-completed audit rows. Merely viewing Hallowed Core intentionally does not adopt it into the generic platform.

The previous setup transaction selected a guild row for update without checking whether it existed, updated zero rows, then inserted module rows referencing that absent parent. An isolated real PostgreSQL reproduction returns 23503, foreign-key violation. No Discord operation is needed to trigger this defect. The candidate explicitly creates the parent first during confirmed Owner setup.

A second issue was found in the production write boundary: the HTTP layer used the standard-guild activation allowlist, which excludes native Hallowed Core. It could therefore refuse Hallowed setup with 403 before reaching the latent database defect. The candidate uses the existing production-writable-guild policy at HTTP and service boundaries; this includes only currently authorized guilds, not LMOC or arbitrary invited guilds.

Known route, input shape, function and SQL failure are documented above. The historical authenticated actor, exact payload, guild and exception are unknown. No authenticated production setup mutation was attempted. The original 500 must not be claimed as exactly reproduced. Old response handling had no usable request correlation; new diagnostics address that gap.

2. Setup fix

Setup now requires current Owner authority, a successful read-only preflight, explicit confirmation, a matching preview digest and an expected state revision. It uses a per-guild PostgreSQL advisory lock and journal revision.

The confirmed operation creates a missing parent configuration row before child rows, inserts missing module/entitlement records idempotently, preserves existing module configuration and existing non-null settings, and records completion once. Setup still creates no Discord roles, channels, categories, forums, commands, scheduled jobs or Gateway clients. Its preview says so explicitly.

Hallowed Core defaults remain separate from standard-guild defaults. The native FAITH/GAMING/TECH policy, human-reviewed additional access and Owner protection are not copied into generic future guilds.

3. Setup state machine

The API exposes an observed state, classification, revision, safe-retry flag, eight named stages, resource preview, update time and diagnostic references. Observed initial states include NOT_INSTALLED/PREFLIGHT; existing unjournaled configuration is VERIFYING. Confirmed attempts persist CONFIGURING, followed by READY or DEGRADED. The contract supports the other requested state labels without pretending every label represents an executed operation.

Classifications are ALREADY_CONFIGURED, PARTIALLY_CONFIGURED, READY_TO_CONFIGURE and BLOCKED. Stages are Bot Connected, Permission Check, Guild Preflight, Database Setup, Role/Channel Configuration, Command Verification, Runtime Verification and Ready.

The journal uses the existing platform-record table under a reserved system-setup collection. There is no new production table or startup migration.

4. Resume and uncertain outcomes

A confirmed journal survives a later configuration failure. Configuration writes are transactional; failed module inserts roll back while the recovery journal remains. The UI displays the failed step and reference, discards the stale preview and requires a new preview and confirmation before Resume.

A live lease and revision checks refuse overlapping attempts. A stale lease can be resumed after fresh checks. Completed module configurations are not reset. Lost final commit acknowledgments cannot overwrite committed READY with a failure: the recovery update is conditional on the same attempt still being CONFIGURING. Repeated identical setup returns already configured without another completion audit or resource creation.

5. Errors and telemetry

Admin responses distinguish 400, 401, 403, 404, 409, 422, 429, 503 and 500. Known dependency failures and validation conditions are not unexpected 500s. Error bodies contain a short safe message and reference ID.

Member commands retain an explicit allowlist of safe business guidance, but no longer echo arbitrary exception messages. Raw SQL, cache exceptions, source paths, credentials and environment contents are not returned to members.

Structured request logs contain correlation ID, guild, operation, stage, response status, elapsed duration, dependency durations and call counts. Failure logs add a safe failure class and recognized dependency code, without bodies, tokens or SQL. Responses include X-Request-ID and Server-Timing. Recent diagnostic references are bounded and guild-scoped; they reset with the process, not a durable log archive.
